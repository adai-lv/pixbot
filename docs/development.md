# Pixbot 开发操作规范

> 本文件只规定系统设计、Rust 编码、测试与发布验收的**操作细节与判定方式**：AGENTS.md 已用一句话写明的规则，本文件只写如何判定、如何取证，不复述规则正文。规则与 DoD 的唯一权威入口是 [AGENTS.md](../AGENTS.md)；技术语义以 [架构总览](architecture.md) 和[领域设计导航](architecture.md#领域设计导航) 为准；交付顺序与版本出口以 [路线图](roadmap.md) 为准。
>
> 当前实现以 `apps/` 源码与测试为准；下文中的**目标／规划**能力不得解释为已实现事实。

## 1. 使用方式

### 1.1 适用范围与生效标记

本规范适用于 `apps/` workspace 的生产代码、测试、文档和发布活动，不适用于 `apps/target/` 生成物或 `resources/pi/` 固定参考快照。

| 标记 | 含义 |
|---|---|
| `[已生效]` | 当前仓库即可执行；不代表所有历史代码已经通过 |
| `[M0 起]` | 对应 crate 或能力落地后强制执行 |
| `[工具引入后]` | 指定工具按依赖流程引入后执行，引入前使用写明的替代判定 |
| `[条件验收]` | 样本、基线或运行条件存在时执行，否则记录 `N/A` 及原因 |

“强制”条款未通过不得合入或发布；“推荐”条款偏离时应在任务规格或评审记录中说明理由。任何检查都只能记录实际执行结果，不能用目标状态代替验收证据。

pi 的实际行为以 `resources/pi/` 源码为唯一事实来源，索引见 `resources/pi-architecture.md`；该目录是第三方参考快照，不是 Pixbot 实现代码，本规范不据它推导 Rust 验收规则或当前实现状态。三类事实须分层书写：**当前已实现**由 `apps/` 源码证实，**目标／规划**是 Pixbot 自身设计，**pi 快照实际行为**只作参考对照，不得混写。

### 1.2 开工与权威导航

**SD-40【强制】先定边界再实施** `[已生效]`

开工前按 [AGENTS.md 的改动流程](../AGENTS.md) 确认范围与必要工作文档：Spec／Plan／Issue 的适用门槛、TODO 用法与 memory 恢复对账只在该文件维护，本文件不复制。此处只补充三条操作要求：

1. 实现不得超出 Spec 或 Issue 范围；需要扩大范围时先停下，更新并确认对应契约，必要时补建 Plan。
2. 技术语义冲突时回改本文件对应条款，不在本文件另建一套架构权威。
3. 需要模板时按类型进入 [Specs](../.agents/specs/README.md)、[Plans](../.agents/plans/README.md)、[Issues](../.agents/issues/README.md)。

判定原则：工作文档按改动复杂度启用，强制 Spec → Plan 链路会让局部修复的流程成本高于改动本身。

| 需要确认的内容 | 权威来源 |
|---|---|
| 项目规则、禁止事项与 DoD | [AGENTS.md](../AGENTS.md) |
| crate 分层、全局不变量、性能目标、外部依赖 | [架构总览](architecture.md) |
| Agent、上下文、会话、工具、安全、Provider 行为 | [领域设计导航](architecture.md#领域设计导航) |
| 里程碑范围与出口 | [路线图](roadmap.md) |
| 已实现 Rust 契约 | 代码、serde 属性与测试；导航见 [API 文档](api/README.md) |

### 1.3 研发专家团

本节约定使用 Claude Code 项目级 Agent 开发 Pixbot 的协作方式。六个角色配置位于 `.claude/agents/`，项目规则仍以 [AGENTS.md](../AGENTS.md) 为唯一权威入口；默认模型和工具清单以各 Agent 文件的 frontmatter 为准。

#### 角色与职责

六个角色：PEL 资深产研主理人（统一入口、分类分派、质量决策）、PM 产品经理（用户价值、场景、优先级、产品 AC）、SA 系统架构师（边界、公共契约、不变量、取舍）、SE 系统工程师（模块拆解与 Rust 实现）、TE 测试工程师（测试设计与回归执行）、QA 质保工程师（独立评审与 DoD 核对）。

伊拉负责“为什么做、做什么”，塞隆负责“技术上怎样构成”，凯南负责“怎样落地”；诺维产出测试证据，奥罗独立检查证据，哈兰作交付协调与质量决策。用户保留 Spec 确认、范围扩张、新增依赖、外部副作用、commit、push、打标签和发布的决定权。

#### 模糊需求的原生澄清

本节是研发专家团需求澄清的唯一完整流程。常规研发任务由哈兰主持，使用专家团自身规则完成，不调用外部 brainstorming skill，不新增专用澄清角色。简单咨询、事实查询和边界明确的机械修改不进入完整流程；目标、范围、设计或验收模糊的需求必须完成下述流程，不得带着关键未决项直接开工。

哈兰是唯一用户对话窗口和流程负责人。伊拉、塞隆、诺维等专家按实际信息缺口参与，向哈兰提供“建议下一问、提问原因、候选答案及影响”，由哈兰转换成一次用户提问，不另开多条用户提问线。对话状态只分为**已确认事实**、**当前假设／项目默认**和**未决问题**；已确认内容不重复询问，答案推翻前结论时显式标记失效。

各角色在澄清中的分工与边界以 `.claude/agents/` 中对应文件为准：哈兰选择下一问并整合 Spec，伊拉提供价值与产品 AC，塞隆提供边界、契约与异常语义，诺维核对 AC 可执行性，凯南只在可实施性有疑问时提供事实，奥罗在需要独立复核时检查未决项与证据。

完整澄清按以下顺序推进：

1. **建立问题框架**：哈兰复述用户目标，列出已知事实、当前假设、未决问题和需要参与的专家，区分当前行为与目标设想。
2. **逐题澄清**：每次只问一个影响后续决策的问题，优先提供可判断的选项。按“目的与价值 → 场景与范围 → 约束与明确不做 → 技术取舍 → 验收标准”推进；不适用的阶段明确跳过，不机械使用固定题单。
3. **形成方案选择**：整理 2–3 个可行方案，说明取舍并给出推荐。产品与技术判断分别由对应专家提供，用户选定后才展开目标设计。
4. **分段确认设计**：按复杂度呈现单元职责、关键流程、异常和验收，每段确认后继续；出现异议时回到对应未决项，不带着冲突往下写。
5. **沉淀并确认 Spec**：哈兰整合专家内容形成一份 Spec。目标、范围、方案、异常和 AC 均有结论且不存在阻塞未决项后，才请求用户确认；只有用户明确确认才能把 Spec 标为“已确认”并进入实施。

澄清阶段不得编写生产代码、搭建实现骨架或以试验为名绕过设计确认。完整澄清要求所有必要结论都有着落，不要求固定问题数量或所有专家出场。

异常与中断按以下规则处理：

- 用户不确定时，哈兰给出推荐默认值及影响，由用户决定是否接受，不编造用户决定。
- 答案冲突时暂停后续设计，回到最早影响冲突的问题；触及既有架构或禁止事项时指出具体权威规则，确需改变时先确认范围变化。
- 需求包含多个独立子系统时先拆分，再选择第一个子项目澄清，不以一份 Spec 承载多个独立目标。
- 用户终止时记录关闭原因或恢复信息，不把讨论过写成已确认；用户要求跳过讨论也不自动豁免项目 Spec 门禁。
- 跨会话中断时，同一任务的 memory 只记录当前阶段、下一个具体问题、未核对改动和恢复核对项，不复制完整问答，不建立角色私有记录。
- 专家未实际参与时明确披露；其负责的阻塞问题未解决时不得确认 Spec。

#### 统一入口、质量流程与 `.agents` 责任

常规研发任务通过 `@agent-pixbot-pel` 或 `claude --agent pixbot-pel` 交给哈兰；简单咨询与边界明确的机械修改不进入完整流程。默认参与角色随任务类型确定：生产代码改动包含凯南、诺维、奥罗，涉及设计时增加塞隆，涉及产品价值时增加伊拉。每次委派必须提供目标、背景、权威文档、允许修改的路径、验收标准、禁止事项和预期输出；默认在同一工作树顺序修改，只有相互独立的只读调研可以并行，不默认使用 worktree。

质量流程固定为：恢复与分类 → 产品与技术设计 → 实施准备 → 开发与验证 → 独立质保 → 收尾与决策。失败交回凯南，不删除必要断言、不靠重跑碰运气、不隐瞒未执行项；未解决问题退回对应专家，不由哈兰直接关闭。专家调用失败、评审未发生或验证未执行时必须明确披露，不得由哈兰冒充对应专家形成独立结论；奥罗的独立性是独立上下文审查，不是强制审批系统，工具 allowlist 也不是 Bash 命令级沙箱。

`.agents` 工作文档按 [AGENTS.md 的目录职责](../AGENTS.md) 与各目录规范维护：同一任务只由哈兰整合一个 memory 块，不启用角色私有 memory；Spec 只有用户明确确认后才能标为“已确认”；Plan 不重定范围；公共契约、跨模块或范围扩大时 Issue 升级为 Spec。commit、push、打标签、发布与历史修改须用户逐项明确要求，任何人不得擅自执行。

## 2. 系统设计操作约束

### 2.1 内存、并发与遍历

**SD-01【强制】lib 代码零 panic** `[已生效]`

规则见 [AGENTS.md 的代码风格](../AGENTS.md)。判定：`#[cfg(test)]` 与 `tests/` 可按测试需要放宽；附录 A.2 的 grep 只用于发现候选命中，命中测试代码仍须人工分类，不能自动判绿。

**SD-02【强制】锁中毒恢复且不跨 `await` 持 std 锁** `[已生效；异步场景随实现生效]`

`std::sync` 锁中毒统一使用 `unwrap_or_else(|e| e.into_inner())` 恢复。锁守卫不得跨 `await` 存活；先取数据并释放守卫，再做异步 IO，确需异步锁时明确所有权与临界区。评审结合 clippy 的 `await_holding_lock` 检查。

**SD-03【强制】端口对象可跨线程** `[M0 起]`

跨 tokio 任务传递的端口 trait 对象满足 `Send + Sync`，DTO 与事件满足实际消费者要求的 `Send` 约束；由 trait 定义和编译期使用共同验证。

**SD-05【强制】递归与输出必须有界** `[M0 起]`

树链、转录或嵌套事件遍历采用迭代或显式深度预算，预算及理由写入任务规格。工具大输出按 [工具设计](design/tools.md) 截断或落盘，避免无界驻留内存和循环内反复克隆增长。

**SD-07【推荐】所有权优先于克隆**

API 边界优先借用；跨任务或跨组件确需所有权时再克隆。评审重点检查循环、热点转换和大消息副本。

### 2.2 crate 边界与数据契约

| 条款 | 操作约束 | 判定 |
|---|---|---|
| **SD-10** `[已生效]` | 除架构定义的 bootstrap 装配例外外，跨 crate 通信只经 `contracts` 的端口、DTO、事件与纯函数；端口 trait 不定义在其他 crate | 核对依赖清单与 trait 定义位置；运行 CD-14 的架构守卫 |
| **SD-11** `[已生效]` | 编译期依赖只沿 `L5 → L4 → L3 → L1/L2 → L0`，L1/L2 层内及相互之间禁呼，由装配层注入 | 架构守卫以结构化 cargo metadata 判定依赖图，并检查原始 manifest；不得靠文本猜测依赖边 |
| **SD-12** `[已生效]` | `contracts` DTO 保持协议中立，不引入运行时、HTTP／协议 SDK 或 C 编译依赖 | 核对 `apps/crates/contracts/Cargo.toml` 与新增依赖评审 |
| **SD-13** `[已生效]` | 持久化字段与 append-only 规则见 [AGENTS.md](../AGENTS.md)，本条款只限定判定方式 | 旧 payload／JSONL 可读性和默认值有回归断言；无持久化实现时不虚构测试已通过 |
| **SD-14** `[M0 起]` | 事件顺序、错误流、工具配对和 `run()` 收尾遵循 Agent 与工具设计 | 按 [Agent 设计](design/agent.md) 和 [工具设计](design/tools.md) 写契约回归，不在本规范复制算法 |
| **SD-15** `[M0 起]` | 领域消息到 wire 消息只在上下文转换边界降级，Provider 不感知扩展变体 | 按 [上下文设计](design/context.md) 覆盖每种适用变体和异常路径 |

新增 crate 前先核对 [架构总览](architecture.md) 的拆分门槛；不满足时优先在现有 crate 内建立模块边界。

### 2.3 依赖管理

**SD-20【强制】版本只在 workspace 声明** `[已生效]`

规则见 [AGENTS.md 的代码风格](../AGENTS.md)。判定：附录 A.2 提供清单守卫；`package.version.workspace = true` 不属于依赖私锁版本。

**SD-21【强制】新增依赖先评审再声明** `[已生效]`

依次完成：任务规格记录需求、备选方案和“不引入”选项；更新 [架构总览的外部依赖清单](architecture.md)；长期取舍追加 [ADR](decisions.md)；以最小 features 写入 workspace 清单；执行全量门禁。HTTP 客户端、TOML 解析等尚未选型的能力不得预先写成既定依赖。

**SD-22【强制】避免同类重复与第二运行时** `[已生效]`

异步运行时使用 `tokio`，序列化使用 `serde` 系，CLI 解析使用 `clap`。新增同类库必须说明替换关系；`cargo tree -d` 用于审查重复版本，不单独证明“同类能力唯一”。

**SD-23【强制】区分构建依赖与工具链工具** `[已生效]`

`cargo-audit`、`cargo-deny`、`cargo-machete`、`llvm-cov` 等工具经开发环境安装，不进入 workspace 构建依赖。作为库使用的 `proptest`、`criterion` 即使是 dev-dependency，也按 SD-21 登记和声明。

**SD-24【推荐】依赖升级可审查**

补丁和小版本升级说明影响；major 升级单独评审并跑全量门禁。升级不能夹带无关功能改动。

### 2.4 错误处理

**SD-30【强制】每 crate 一个 `thiserror` 错误枚举** `[已生效]`

生产 crate 的可恢复失败由一个顶层错误枚举分类承载，错误文本包含定位上下文，不丢失来源。跨 crate 端口只暴露 contracts 中立错误，内部错误必须在适配边界映射；端口名称不要求 contracts 定义多个 thiserror 枚举，具体形状由 `0.1.0` 规格固定。新增变体须同步端口语义和异常路径测试，不用字符串重新分类。

**SD-31【强制】`anyhow` 只在边界** `[已生效]`

只有 `cli` / `bootstrap` 边界可用 `anyhow` 汇总；L0/L1/L2 lib 代码不得使用。依赖清单和源码均需核对。

**SD-32【强制】错误进入结果，不进入 panic 或静默吞掉** `[M0 起]`

工具失败、取消、拒绝、截断和落盘异常的结果回填语义以 [架构总览的核心不变量](architecture.md) 与领域设计为准；核心异常路径必须断言调用方可观察的结果。确需忽略 `Result` 时显式写 `let _ = expr;` 并附理由，不能借此隐藏需要回填的错误。

**SD-33【推荐】保留错误分类**

`#[from]` 只用于原样上抛且不丢分类的场景；需要附加上下文时使用 `map_err` 或手写转换。

## 3. Rust 编码规范

### 3.1 格式、命名与模块

**CD-01【强制】rustfmt 使用登记的 stable 最小配置** `[已生效]`

`cargo fmt --all -- --check` 必须零 diff。当前 `apps/rustfmt.toml` 只配置 `edition = "2024"`；允许在该文件增量登记 stable 通道支持且全 workspace 一致的 minimal 配置，并在任务规格说明选项与理由，长期取舍同步 ADR。禁止本地私有格式配置和未被当前工具链支持的 nightly-only 选项。

**CD-02【强制】Edition 与 MSRV 锁定** `[已生效]`

Edition 与 MSRV 见 [AGENTS.md](../AGENTS.md)。判定：不得使用 1.93 之后才稳定的 API；发布前执行附录 A 的 `cargo +1.93 check --workspace` 并记录结果。

**CD-03【强制】命名与规模可维护** `[已生效；规模随 crate 落地]`

文件和模块用 `snake_case`，类型用 `PascalCase`，常量用 `SCREAMING_SNAKE_CASE`；集合类 crate 用复数，单一机制或领域用单数，端口名用单数。crate 拆分与 `agent` / `tools` 规模阈值以 [架构总览的拆分门槛](architecture.md) 为准，超限先拆模块或评审拆 crate。

**CD-05【推荐】导入与调试痕迹**

`use` 按 std、外部 crate、workspace crate、本 crate 分组；不提交注释掉的代码或 `dbg!`。稳定 rustfmt 尚不支持的导入选项不得写入配置文件冒充已生效。

### 3.2 unsafe 与 lint

**CD-10【强制】默认零 unsafe** `[已生效]`

生产代码默认禁止 `unsafe`，`contracts` 不允许例外。确因性能或 FFI 必须引入时，先记录 ADR，再给每个块添加紧邻的 `// SAFETY: <不变量及成立理由>`，为 `unsafe impl Send/Sync`、`mem::transmute` 提供属性测试或等价覆盖，并登记附录 B。

**CD-11【强制】workspace clippy 门禁** `[已生效]`

- **已生效**：提交前和 CI 执行 `cargo clippy --workspace --all-targets -- -D warnings`，要求零告警。

## 4. 自动化测试规范

### 4.1 测试矩阵与权威覆盖来源

**TS-01【强制】按测试目的选择位置** `[已生效，范围随实现扩大]`

| 层 | 位置与外部 IO | 核心要求 |
|---|---|---|
| 单元测试 | crate `src/` 内 `#[cfg(test)]`；无外部 IO | 覆盖纯函数、状态转换与错误分类 |
| 集成测试 | crate `tests/`；使用 tempfile 与 crate 私有替身 | 验证真实组件协作，不读写开发者真实目录 |
| 契约回归测试 | 对应领域 crate；本地 fake transport／可控端口替身 | 验证跨组件可观察契约和结果回填 |
| 属性测试 | 纯函数域；无外部 IO | 有界策略、可复现 seed；工具未引入前用表驱动穷举替代 |

具体行为和分期不在这里复制第二份清单，按改动领域使用下列权威矩阵：

| 领域 | 测试语义权威来源 |
|---|---|
| Agent 循环、事件、取消与恢复 | [Agent 设计](design/agent.md) |
| 投影、转换、压缩与缓存 | [上下文设计](design/context.md) |
| JSONL、会话恢复与用量 | [会话设计](design/session.md) |
| 工具参数、并发、结果与内建工具 | [工具设计](design/tools.md) |
| hooks、sandbox、配置与密钥 | [安全设计](design/security.md) |
| 协议流、认证、目录与 Provider 基线 | [Provider 设计](design/providers.md) |
| 当前版本必须交付的测试范围 | [路线图的分版本出口](roadmap.md) |

真实 Provider 凭据 e2e 只显式 opt-in，不进入普通 CI；离线契约与真实 smoke 的结果分开记录。

### 4.2 通用测试要求

| 条款 | 操作要求与判定 |
|---|---|
| **TS-02** `[已生效]` | 每个生产行为覆盖正常、边界和异常路径；核心契约异常路径断言结果回填，不只断言“未 panic” |
| **TS-03** `[已生效]` | fake、fixture、scripted mock 留在各 crate 测试代码；生产 `contracts` 不承载替身，不建立共享 `testkit` |

### 4.3 用例编写与稳定性

**TS-10 / TS-11【强制】行为命名与 AAA** `[已生效]`

测试名表达被测物、条件和预期，避免 `test1`、`test_ok`。测试体按 Arrange / Act / Assert 组织，一个测试聚焦一个行为，断言可观察结果而非私有实现细节。

**TS-12【强制】隔离时间、顺序与共享状态** `[已生效]`

测试间不共享可变全局状态；临时目录唯一，时间逻辑注入时钟或受控时间。里程碑验收对比默认并发与 `--test-threads=1`；异步等待使用有界条件等待，不用无期限 sleep。

**TS-13【推荐】同型用例表驱动**

同型多输入优先表驱动并保留用例名；属性测试尚未引入时，用边界表覆盖关键输入域。

**TS-30 / TS-31【强制】通过率与 flaky 零容忍** `[已生效]`

普通测试不允许失败，不能用重跑碰运气过闸。忽略测试必须写 `#[ignore = "reason: <原因与跟踪任务>"]`；不稳定测试当次修复，或带理由和跟踪项显式降级。

**TS-32【强制】覆盖率工具与阈值分阶段** `[工具引入后]`

引入 `llvm-cov` 前，以 TS-02 三路覆盖和核心结果回填作为替代判定，不声称已有覆盖率数值。引入后，新增／修改行覆盖率目标为 80%，任务规格认定的核心契约模块累计行覆盖率目标为 90%；未达标须修复或记录经评审的例外。

### 4.4 性能基准

**TS-20【强制】基准随适用机制建立** `[M0 起；criterion 引入后自动化]`

基准对象从 [架构总览的性能目标表](architecture.md) 和当前里程碑实际机制选择，输入形态与生产同构。criterion 未引入前可在任务规格中手工测量；首次测量只建立基线，没有历史基线时回归项记 `N/A`，不得宣称“无回归”。

### A.2 grep 守卫

以下函数在**仓库根目录**执行，路径使用根目录相对的 `apps/crates`。它明确区分 grep 的 `0=命中`、`1=无命中`、`>1=执行错误`；目录不存在和参数错误均失败，不会假绿。

```bash
guard_no_match() {
  if [ "$#" -lt 2 ] || [ "$#" -gt 3 ]; then
    printf 'ERROR: usage: guard_no_match PATTERN DIRECTORY [GLOB]\n' >&2
    return 2
  fi

  pattern=$1
  directory=$2
  glob=${3:-'*.rs'}

  if [ ! -d "$directory" ]; then
    printf 'ERROR: directory not found: %s\n' "$directory" >&2
    return 2
  fi

  if grep -rn -E --include="$glob" -- "$pattern" "$directory"; then
    status=0
  else
    status=$?
  fi
  case "$status" in
    0)
      printf 'FAIL: matches require review in %s\n' "$directory" >&2
      return 1
      ;;
    1)
      printf 'PASS: no matches in %s\n' "$directory"
      return 0
      ;;
    *)
      printf 'ERROR: grep exited %s for %s\n' "$status" "$directory" >&2
      return "$status"
      ;;
  esac
}

guard_no_match '\.unwrap\(\)|\.expect\(|panic!|todo!|unimplemented!|unreachable!' apps/crates
guard_no_match '\bunsafe\b' apps/crates
guard_no_match 'version[[:space:]]*=[[:space:]]*"' apps/crates Cargo.toml
guard_no_match 'dbg!' apps/crates
```

这些调用是审阅辅助，不代表架构守卫或 restriction lints 已接入 CI。生产代码出现禁止命中即违例；测试代码的 panic 类命中须按 SD-01 人工分类。函数对任何命中返回失败，不会擅自豁免测试目录。

依赖守卫入口见 CD-14。结构化 metadata 检查生产 `[dependencies]` 及 Cargo 归一化后的 target-specific 生产依赖，原始 manifest 文本检查版本唯一来源，另有公共 trait 位置扫描；`dev-dependencies`／`build-dependencies` 不在本版方向守卫范围。普通 workspace 测试不递归进入 `--self-test`，完整正负例只由显式参数执行。
