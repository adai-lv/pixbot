# 决策记录

> 本文件是 Pixbot 长期技术取舍的唯一权威来源。它只记录「决定什么、为什么、代价是什么」，不承载现行技术正文（正文在 `docs/architecture.md` 与各领域设计），也不复述实现状态。
>
> 记录规则：
>
> - **追加维护**：改变既有决策时新增 superseding ADR 并更新全部现行引用，不改写历史来制造「当时已如此」的假象。
> - **范围**：只保留仍在指导实现的取舍。已完整成文于架构、领域设计或工程规范、且不再需要单独解释取舍的约束，不再重复保留 ADR，其现行语义以对应文档为准。
> - **状态**：只描述决策本身（采纳／已取代），不代表实现进度；实现分期见各条「阶段」，行为事实以 Rust 代码与测试为准。
> - **编号**：从 `ADR-001` 起连续编排，新增条目在末尾续编，既有编号不重排、不复用于不同决策。
> - **正文单一**：每条 ADR 的技术正文只保留链接，现行解释以链接文档为准，本文件不保留第二份实现细节。

## 条目格式

新增 ADR 从最大编号加一续编，固定使用以下字段；某字段确实不适用时写「不适用」并给出理由，不得省略字段。

```markdown
### ADR-0NN · <决策标题>

- **状态**：采纳 ｜ 已取代（→ ADR-0NN）
- **阶段**：M0 起 ｜ M1 起 ｜ M2 起 ｜ 全阶段（不绑里程碑）
- **背景**：<要解决什么问题，冲突在哪里>
- **选项**：A …；B …；C …。选择 B。
- **决策**：
  - D1 …
  - D2 …
- **后果**：收益 <…>；代价 <…>。
- **影响面**：<crate / 文档 / 不变量>；<变更时的约束>
- **相关**：ADR-0NN（关系说明）
```

约束：一条 ADR 只承担一个可判定的取舍；「后果」必须同时写出收益与被放弃的东西；「影响面」不改写历史，只说明后续变更需要保持什么。

## 决策条目

### ADR-001 · 内核三职责与端口化边界

- **状态**：采纳
- **阶段**：M0 起
- **背景**：若内核直接实现 provider 协议、工具行为、持久化格式与前端渲染，任何一处改动都会穿透决策循环；参考设计也没有给出「什么必须留在内核」的判定线。
- **选项**：A 内核承担全部能力；B 内核只维护转录、驱动模型与工具循环、暴露事件，其余经编译期端口注入；C 内核只做消息转发。选择 B。
- **决策**：D1 内核唯一持久状态是转录，运行期状态限于双队列、取消令牌与未完成调用集合；D2 循环只做决策与调度，不实现协议映射、工具语义、安全策略或 UI；D3 前端只消费 `AgentEvent` 流并取得 `RunOutcome`，不持有内核状态；D4 扩展形态固定为编译期端口承载行为扩展、进程外协议承载生态扩展。逐条契约见[架构·设计立场](architecture.md#设计立场)与[全局边界](architecture.md#全局边界)。
- **后果**：收益是端口可替换、循环可独立测试、内核不随 provider 与工具数量膨胀；代价是每次能力扩展都要新增端口与 DTO，跨 crate 改动面变大。
- **影响面**：`contracts` 端口与 DTO、`agent` 模块划分、`architecture.md#全局边界`；后续新增能力不得把实现细节下沉进内核。
- **相关**：ADR-002（转换边界）、ADR-005（事件契约）、ADR-008（装配归属）

### ADR-002 · 领域消息与 wire 消息双轨制

- **状态**：采纳
- **阶段**：M0 起
- **背景**：领域消息需要承载 `is_meta`、工具结果、压缩等扩展变体，wire 消息只有 system／user／assistant／tool 四种角色；若 Provider 直接理解领域变体，每个适配器都要随变体重写，厂商 JSON 也会渗进内核。
- **选项**：A 单一消息类型贯穿全层；B 领域消息与 wire 消息双轨，转换只发生在一个边界；C 每个 provider 自带领域模型。选择 B。
- **决策**：
  - D1 领域 → wire 只经 `ContextEngine::to_wire`，Provider 适配器只做 wire → 厂商 JSON 的字段映射。
  - D2 `is_meta=true` 的条目不进入模型请求，仅供前端与落盘。
  - D3 领域变体的降级决策归上下文层，Provider 不感知扩展变体。
  - D4 M0 只做 `to_wire` v1；新增持久化字段必须带 serde 默认值。
- **后果**：收益是领域可扩展、wire 稳定、适配器数量与变体数量解耦；代价是两套模型需同步演进，`to_wire` 成为热点并要为每个变体写回归。
- **影响面**：`contracts` 消息模型、`context`、`providers`；对应核心不变量「中立请求边界」，变更需同时改这三处与不变量表。
- **相关**：ADR-003（转录形态）、ADR-011（M0 转换范围）

### ADR-003 · 转录单一事实源与只追加持久化

- **状态**：采纳
- **阶段**：M0 起（树与分支能力自 M1）
- **背景**：若界面状态、缓存和会话文件各存一份历史，恢复、缓存与审计会互相矛盾；而原地改写历史又会让「回放」与「当时的记录」不再等价。
- **选项**：A 内存或界面为事实源、文件只作导出；B 转录为唯一事实源、持久化只追加；C 每次运行重放工具产出。选择 B。
- **决策**：D1 转录为唯一事实源，会话文件只追加、历史修正以追加条目表达；D2 M0 只有线性 `TranscriptEntry::Message`；D3 M1 才追加 `Compaction`／`Label`／`ContextEdit` 与分支、fork 能力；D4 用量写独立 `UsageRecord` 台账；D5 坏行跳过、孤儿不入投影、写盘失败只告警。逐条见[会话设计](design/session.md)。
- **后果**：收益是回放自洽、恢复与缓存同源、审计可追溯；代价是「改写」必须用追加条目表达，M0 不具备压缩恢复与分支能力，且防抖写入扩大了崩溃时的未落盘窗口。
- **影响面**：`session`、`context`；`design/session.md` 的布局与写入纪律、AGENTS.md 的 serde 默认值规则。
- **相关**：ADR-002（消息形态）、ADR-011（M0 线性边界）

### ADR-004 · 双层循环与 steering／follow-up 双队列

- **状态**：采纳
- **阶段**：M0 起
- **背景**：单层「请求—执行工具」循环只能处理工具批次，无法表达运行中追加指令（不打断已发出的调用）与「本应停止时再补一轮」两种不同语义；合成一个队列会让干预点不可判定。
- **选项**：A 单队列；B 双层循环 + steering／follow-up 双队列，默认 `one-at-a-time`；C 每条新消息启动新 run。选择 B。
- **决策**：D1 内层循环处理工具批次、外层处理续跑；D2 steering 在工具批次结束与下次请求前排空，不打断已发出的调用；D3 follow-up 仅在本应停止时至多触发一次重入，预算耗尽后消息留在队列；D4 两类续跑各一次独立预算；D5 取消默认保留队列，`run()` 不可重入。逐条见[Agent 设计的队列与收敛](design/agent.md#队列与收敛)。
- **后果**：收益是干预语义完整、排水点可测、预算不会互相掩盖；代价是实现与测试成本高，队列排水点成为必须锁定的契约。
- **影响面**：`agent` 的 `driver`／`state`；`design/agent.md` 的主循环、队列表与预算说明。
- **相关**：ADR-005（结束语义）、ADR-011（预算落地）

### ADR-005 · 事件层级与 settled 语义

- **状态**：采纳
- **阶段**：M0 起
- **背景**：前端需要无状态重建视图；若结束点既有结束事件又有返回值，收尾、退出码与「还能不能发事件」会同时存在两种解释。
- **选项**：A 扁平事件 + 独立结束回调；B 嵌套事件 + `run()` resolve 即 settled + 返回 `RunOutcome`；C 只返回结果不暴露事件。选择 B。
- **决策**：D1 事件层级为 `AgentStart` → `TurnStart` →（`Message*`／`ToolExecution*`）→ `TurnEnd` → `TurnComplete`；D2 `TurnComplete` 恒为最后事件，`Error`／`Notice` 为带外事件；D3 `RunOutcome` 是返回值而非第二个结束事件，`run()` resolve 即 settled；D4 `ModelStopReason` 与 `RunStopReason` 分型；D5 user／system／`tool_result` 消息不产生 `MessageUpdate`。逐条见[Agent 设计的事件与结果类型](design/agent.md#事件与结果类型)。
- **后果**：收益是视图可重建、退出码有唯一来源、结束点无二义；代价是事件顺序成为公开契约，新增事件必须显式声明插入位置与「是否在 settled 之前」。
- **影响面**：`contracts` 事件 DTO、`agent` 的 `events` 模块、前端 drain／flush；对应核心不变量「结束唯一」。
- **相关**：ADR-001（事件暴露职责）、ADR-006（失败如何进事件）

### ADR-006 · 截断安全、配对铁律与错误编码进结果

- **状态**：采纳
- **阶段**：M0 起（压缩切点自 M1）
- **背景**：三类真实事故会静默污染上下文——截断后仍执行工具、`tool_use` 没有对应结果、失败只写进文本内容。它们都会让模型与用户看到虚假成功。
- **选项**：A 由各工具自行保证；B 内核强制三类不变量并在所有异常路径回填结果；C 失败时直接终止 run。选择 B。
- **决策**：D1 每个 `tool_use` 有且仅有一个 `tool_result`，未知工具、参数错误、取消、最终模型错误、截断与落盘失败都必须回填 `is_error=true`；D2 停止原因为 Length 时整批工具不执行；D3 失败语义只从 `ToolResult.is_error` 读取；D4 工具返回的 `Err` 由 dispatch 归一化为错误结果；D5 M1 压缩切点不得落在 `tool_result`。逐条见[架构·核心不变量](architecture.md#核心不变量)。
- **后果**：收益是三类事故有可执行回归防线，模型永远看得到配对的失败；代价是每个异常分支都要构造结果，测试矩阵显著变大。
- **影响面**：`agent` 的 `dispatch`、`tools`；`architecture.md#核心不变量` 的配对、截断、压缩切点与「错误在结果中」四条。
- **相关**：ADR-007（执行顺序）、ADR-010（错误类型）、ADR-011（M0 落地点）

### ADR-007 · 工具预备串行、执行并行与双序发射

- **状态**：采纳
- **阶段**：M0 起
- **背景**：并行执行能压低批次墙钟，但参数预备可能读文件或探测环境，并发预备会引入竞争；同一文件上的并发写会互相破坏内容。
- **选项**：A 全串行；B 全并行；C 预备串行、执行默认并行、同文件写串行。选择 C。
- **决策**：D1 参数预备严格串行；D2 执行默认并行，全局 sequential 或批内任一工具声明 sequential 时整批顺序；D3 `ToolExecutionEnd` 按完成序、`tool_result` 消息按源序；D4 同文件 `edit`／`write` 按真实路径串行；D5 `terminate` 仅在整批结果都为 true 时提前停止。逐条见[工具设计的执行流水线](design/tools.md#执行流水线)。
- **后果**：收益是墙钟接近最慢工具且写入不互相踩；代价是两套顺序必须同时正确，误用会静默错位，只能靠契约测试兜住。
- **影响面**：`tools` 注册与执行、`agent` 的 `dispatch`；`architecture.md` 性能表的「工具吞吐」目标。
- **相关**：ADR-006（异常路径同样受顺序约束）

### ADR-008 · 装配权归 bootstrap，cli 只选前端

- **状态**：采纳
- **阶段**：M0 起
- **背景**：参考设计把装配权放在交互层且多前端同期；若 `cli` 直接创建适配器，入口就会与 provider、存储的具体类型耦合，前端也无法复用同一内核。
- **选项**：A `cli` 装配全部依赖；B 装配权在 `bootstrap`，`cli` 只选前端，`Core` 只暴露端口与快照；C 每个前端各自装配。选择 B。
- **决策**：D1 `cli` 只解析参数并选择前端，不装配适配器；D2 `bootstrap` 是唯一允许依赖实现 crate 工厂的装配例外；D3 `Core` 只返回端口对象与纯数据快照；D4 前端只经 `AgentSession` 驱动运行；D5 新增前端只增加画像与装配入口。逐条见[架构·装配与前端](architecture.md#装配与前端)。
- **后果**：收益是前端与实现解耦、装配失败可诊断、新增前端成本低；代价是每新增依赖都要改装配画像，端口边界需要常驻守卫才能防止泄漏。
- **影响面**：`bootstrap`、`cli`、`headless`、`architecture.md#装配与前端`；对应依赖规则中的装配例外条款。
- **相关**：ADR-001（内核边界）

### ADR-009 · prompt cache 三纪律

- **状态**：采纳
- **阶段**：M0 起（差量声明与完整机制自 M1）
- **背景**：长编码会话的成本主项是缓存前缀命中；工具注册序抖动、动态内容前插、工具面静默变化都会让前缀失效，而这种失效在功能测试里不可见。
- **选项**：A 依赖 Provider 默认缓存行为；B 三条纪律（稳定注册序、`cacheable` 动态边界、工具差量声明）；C 手工维护 system 块顺序。选择 B。
- **决策**：D1 内建工具注册序稳定，新工具追加末尾；D2 system 稳定分节在前，cwd、日期、记忆与 M1 工具差量等动态内容在后；D3 `cacheable` 是请求装配期的运行时元数据，不是持久化字段；D4 M1 工具面变化以差量声明追加，同名变化按「删除 + 新增」记录。逐条见[上下文设计的 system 装配与缓存元数据](design/context.md#system-装配与缓存元数据)。
- **后果**：收益是前缀稳定、缓存行为可解释，M0 就有可执行的装配纪律；代价是 M0 只有注册序与运行时标记，差量声明与命中率（目标 >80%，尚未测量）要等 M1 才能验证。
- **影响面**：`context` 装配与 `tools` 注册序；`architecture.md` 性能表的「prompt cache 命中」，未实测前不得写成已达标。
- **相关**：ADR-002（转换边界）、ADR-007（注册与执行）

### ADR-010 · Rust 错误与 panic 纪律

- **状态**：采纳
- **阶段**：全阶段（不绑里程碑）
- **背景**：lib 内 panic 会把可恢复失败变成进程崩溃；跨 crate 若用字符串或 `anyhow` 分类错误，端口边界就会丢失来源与分类，调用方无法分支处理。
- **选项**：A 全仓统一 `anyhow`；B lib 零 panic + 每 crate 一个 `thiserror` + `anyhow` 仅边界；C 各 crate 自定错误风格。选择 B。
- **决策**：
  - D1 生产 lib 禁止 `unwrap`／`expect`／`panic!`／`todo!`／`unimplemented!`／`unreachable!`，可恢复失败返回 `Result`；测试代码可放宽。
  - D2 每个 crate 一个顶层 `thiserror` 枚举，变体带定位上下文且不丢失来源。
  - D3 跨 crate 端口只暴露 `contracts` 中立错误，实现 crate 的内部错误必须在适配边界映射。
  - D4 `anyhow` 仅限 `cli`／`bootstrap` 边界使用。
  - D5 锁中毒统一用 `unwrap_or_else(|e| e.into_inner())` 恢复，锁守卫不得跨 `await` 存活。
  - D6 确需丢弃 `Result` 时显式写 `let _ = expr;` 并附理由，不用它隐藏需要回填的错误。
- **后果**：收益是失败可控、错误可分类、崩溃只来自真正的不可恢复场景；代价是边界需要显式映射代码，类型与变体数量增多。
- **影响面**：全部 crate、`AGENTS.md` 的代码风格条款、`development.md` 的错误处理与 lint 判定；clippy restriction lints 尚未配置，不得声称已自动拦截。
- **相关**：ADR-006（错误如何回到模型）

### ADR-011 · M0 可执行契约边界

- **状态**：采纳
- **阶段**：M0 起
- **背景**：M0 的范围、请求归属和异常收尾曾混用后续能力（压缩、完整树、provider 私有请求），导致实现与验收边界不唯一，「M0 完成」无法判定。
- **选项**：A 一次性落地完整条目树与 provider 私有请求；B 先固定中立、线性的最小契约；C 按 provider 分别定义请求类型。选择 B。
- **决策**：D1 M0 的 `TranscriptEntry` 只有基础 `Message` 并线性追加，压缩、microcompact（**Pixbot 自身命名，pi 快照无对应实现**，见[上下文设计](design/context.md#m1-压缩与清理)）、工具差量、完整树投影与 resume／fork 均不在 M0；D2 `CompletionRequest` 是 `contracts` 中立 DTO，由 Context 产出、Provider 消费；D3 两类续跑各一次显式预算，retry／recover 唯一调用点，Abort 不重试；D4 dispatch 为 prepare → before hook → 最终 schema 校验 → execute，after hook 不覆盖 `is_error`、`terminate` 与 usage。逐条见[会话设计](design/session.md)、[上下文设计](design/context.md)、[Agent 设计](design/agent.md)。
- **后果**：收益是 M0 边界可独立测试、协议耦合下降、验收口径唯一；代价是 M0 放弃长上下文恢复与分支能力，后续扩展要新增条目变体与投影路径。
- **影响面**：`contracts`、`agent`、`context`、`session`、`tools`、`providers` 与前端；后续变更须保持旧 JSONL 可读，改变本条时追加 superseding ADR。
- **相关**：ADR-003（M0 线性约束）、ADR-004（预算归属）、ADR-006（异常回填）
