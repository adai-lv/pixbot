# Specs 编写规范

> 本目录保存单次改动的设计规格。项目规则与 DoD 以 [AGENTS.md](../../AGENTS.md) 为唯一权威来源；本文件只规定 Spec 的组织、编写和模板，不复制项目规则。实例导航与跨文档证据分工统一见[工作文档索引](../README.md)。

## 职责与边界

Spec 回答“为什么做、做什么、目标行为是什么、不做什么、怎样算完成”，用于在实施前确认目标、范围、设计和验收契约。完成后的 Spec 是历史记录，不作为当前架构、接口或行为的权威来源。

Spec 不承载逐步实施任务；需要实施计划时，实施顺序、文件级操作和步骤级执行历史写入关联的 [Plan](../plans/README.md)。跨执行恢复中间态及完成后的摘要与经验索引记录到[每日 memory](../memory/README.md)。

## 适用场景

适用与升级门槛以 [AGENTS.md](../../AGENTS.md) 流程为准：新能力、设计取舍、跨模块协调、公共契约及高风险改动必须先创建并确认 Spec；单纯跨文件、机械重命名和链接修正不强制创建。边界清晰、低风险的局部修正和局部 bug 修复使用 [Issue](../issues/README.md)，但仍须有可验证的验收结果；达到 Spec 门槛的复杂 bug 必须补建 Spec，不得只靠 Issue 直接实施。

## 命名与关联

- 文件名为 `YYYYMMDDHH-design-<topic>.md`，例如 `2026110707-design-agent-document-lifecycle.md`。
- 时间前缀使用 Spec 首次创建时的本地时间，格式为四位年份、两位月份、日期和 24 小时制小时；`<topic>` 使用小写 kebab-case。
- 关联 Plan 沿用 Spec 的完整时间前缀和 `<topic>`，命名为 `YYYYMMDDHH-plan-<topic>.md`，不按 Plan 创建时间重新取小时。
- Spec 通过 `../plans/YYYYMMDDHH-plan-<topic>.md` 链接已创建的 Plan；不需要 Plan 时“关联计划”写“无”，需要 Plan 但尚未创建时写“尚未创建”，不得使用失效链接。
- 由 Issue 升级时，在 Spec 中链接原 Issue；未升级时“关联 Issue”写“无”。
- 一次改动只对应一份 Spec；后续追加改动不得静默并入已完成规格。

## 编写与执行流程

1. 阅读 AGENTS.md、[架构总览](../../docs/architecture.md)、相关领域设计、代码与测试，区分当前行为、目标设计和待验证假设。
2. 复制下方模板，替换全部尖括号占位；按实际增删验收行，不留空白示例、未决占位或与任务无关的提示文字。
3. 完成实施前就绪检查后再确认 Spec。Spec 状态只使用“草稿／已确认／进行中／已完成”。
4. Spec 可以独立完成。只有步骤存在明显依赖、需要跨会话实施或高风险操作必须逐步核对时，才在 Spec 确认后创建关联 Plan；有 Plan 时实施顺序以 Plan 为准，验收标准始终以 Spec 为准。
5. 实施开始并写入第一个实际改动后，将 Spec 状态标为“进行中”；实施中止或跨会话恢复时保持“进行中”，恢复游标只记入每日 memory。
6. 实施中需要扩大范围、改变设计或改变验收契约时，先暂停，更新并重新确认 Spec，记录范围变更，再更新可选 Plan 和实施内容。
7. 关键假设失效并影响目标、设计或验收时，回到草稿解决未决项，不带着未确认契约继续实施。
8. 收尾按 AC 编号逐项记录实际结果、失败和未执行项，满足完成门禁后再将状态改为“已完成”。
9. 长期架构、接口、决策或运行变化同步到对应权威文档。

## 实施前就绪检查

- 当前行为有文件、测试、可复现现象或明确观察支撑，不与目标设计、推测混写。
- 影响目标、范围、设计或验收的假设与未决项已经解决；其余假设有明确验证方式。
- 要改与不碰的路径具体，目标设计说明方案、单元职责、关键流程及错误行为。
- 每条 AC 都有场景与操作、可观察预期和可执行验证方式，正常／边界／异常／契约路径已覆盖或说明不适用理由。
- 已判断是否需要 Plan；需要时能在实施前建立 AC 到 P 步骤的覆盖关系。

全部满足后才能将 Spec 标为“已确认”。就绪检查是编写流程的一部分，不需要在 Spec 正文中复制一份。

## 验收与追溯

- 每条验收使用 `AC-01`、`AC-02` 等在 Spec 内唯一的稳定编号。确认后不得静默改写或复用编号；验收变化须重新确认并记录。
- 所有列入验收标准的 AC 默认都是完成门禁。只有实际执行且结果符合预期的检查才能写“通过”；存在失败或未执行项时不得完成 Spec，“不适用”必须说明适用条件为何不存在，不能用于绕过既定门禁。
- 验证方式写测试名、命令或可复现人工操作，写到足以判定结果即可；文件级实施顺序和逐步命令属于 Plan。
- 有 Plan 时，Plan 用 `AC → P → 证据位置` 表覆盖全部 AC；没有 Plan 时，直接在 Spec 收尾记录验证证据。

## 内容约束

- 每份 Spec 只解决一件可说明的事；范围过大时先拆分。
- 目标描述完成后可观察的结果，不把“修改某文件”本身当作目标，避免“完善”“优化”等无法判定的表述。
- 范围使用具体文件或模块路径，不使用“等相关文件”代替边界；范围变化保留原因和确认记录。
- 模板中的按条件占位符触发时必须写清对应内容，不适用时写“无”及必要理由。
- 目标设计描述行为、职责和交互，不复制架构、领域设计、路线图或 Plan 正文；引用时使用相对链接。
- 不记录密钥、真实用户数据或本地会话内容。
- 文档使用一个 H1，标题逐级递进，代码围栏标注语言，链接路径大小写与磁盘一致。

## 内联模板

```markdown
# <任务名>

> 状态：草稿 / 已确认 / 进行中 / 已完成。完成后作为历史记录，不作为现行架构或行为的权威来源。
> 关联计划：<关联 Plan 的相对链接；不需要时写“无”，需要但尚未创建时写“尚未创建”。>
> 关联 Issue：<原 Issue 的相对链接；未升级时写“无”。>

## 目标（可验证）

<完成后可观察、可核对的结果及判定方式，不以修改文件作为目标。>

## 背景与证据

- 问题或动机：<为什么需要本次改动。>
- 权威依据与设计：<规则、架构、领域文档及章节；无则说明。>
- 相关代码：<路径；无则说明。>
- 当前行为：<已实现或已核实的当前行为，明确区别于目标设计。>
- 证据：<文件、测试、复现现象或观察依据。>
- 假设与未决项：<实施前必须解决的假设或问题；无则说明。>

## 范围

- 要改：<具体文件或模块。>
- 不碰：<具体文件或模块。>
- 范围变更记录：<实施中经确认的范围或验收变化；无则写“无”。>

## 目标设计

### 方案与取舍

<已选方案与理由、涉及单元及其职责、重要备选及未选原因，以及架构边界等硬约束；说明当前行为到目标行为的变化。>

### 关键流程

<输入、处理、输出、状态变化及必要的数据流或交互顺序。>

### 接口与数据（按条件）

<涉及公共接口、DTO、事件、持久化或外部协议时：接口与数据形状、兼容要求、异常结果及必要的回填断言；无则说明。>

### 错误、边界与兼容

<失败、取消、无效输入、边界条件、异常结果及必要的回填行为。>

### 安全与可观测性（按条件）

<涉及安全边界、外部交互、敏感数据或运行时排障时：安全约束、失败边界、数据保护要求及可观察的诊断依据；无则说明。>

## 验收标准

| 编号 | 类型 | 场景与操作 | 预期结果 | 验证方式 |
|---|---|---|---|---|
| AC-01 | 正常 | <具体输入、前置条件和操作。> | <可观察结果。> | <测试名、命令或人工核对方法。> |
| AC-02 | 边界 | <空输入、极值、重复操作等。> | <可观察结果。> | <具体验证方法。> |
| AC-03 | 异常 | <失败、取消或无效输入。> | <错误行为及必要的结果回填。> | <具体验证方法。> |
| AC-04 | 契约 | <文档、链接、兼容性或依赖边界检查。> | <可核对结果。> | <具体验证方法。> |

## 明确不做

- <相邻但不属于本次范围的事项；无则说明。>

## 风险、迁移与回滚

- 风险：<影响面及控制方式；无则说明。>
- 迁移：<涉及数据、配置、路径、接口或发布迁移时：迁移步骤、兼容窗口和可执行回滚方式；无则明确写“无”。>
- 回滚：<如何实际撤销本次改动。>

## 收尾记录

| 编号 | 结果 | 实际结果与证据 |
|---|---|---|
| AC-01 | 通过 / 失败 / 未执行 / 不适用 | <逐项填写真实结果、关键输出或证据位置；复制并覆盖全部 AC。> |

- 偏差与范围变化：<实际偏差、确认记录及影响；无则说明。>
- 补充检查与未执行说明：<非门禁检查结果和其他未执行项；无则说明。>
- 文档回写：<实际更新的权威文档；无则说明。>
```
