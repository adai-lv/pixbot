# Issues 编写规范

> 本目录保存边界清晰、低风险的局部修正和 bug 修复记录，可包含实现、回归测试和必要文档。项目规则与 DoD 以 [AGENTS.md](../../AGENTS.md) 为唯一权威来源；本文件只规定 Issue 的组织、编写和模板。实例导航与跨文档证据分工统一见[工作文档索引](../README.md)。

## 职责与边界

Issue 用于记录一个局部问题或 bug 的现象、复现条件、根因、修复范围和验证结果。完成后的 Issue 是历史记录，不作为当前架构、接口或行为的权威来源。

Issue 默认不创建 Plan，直接指导局部修复；不支持 Issue 直接关联 Plan。适用与升级门槛见下方条件；跨文档证据分工见[工作文档索引](../README.md)。已经明确的问题可以直接创建 Issue，不必先建立 TODO，也不得把没有明确问题和验收条件的待办批量转换为 Issue。

## 适用与升级条件

边界清晰、低风险、可明确复现或不涉及架构迁移的局部修正和局部 bug 可只使用 Issue。出现以下任一情况时暂停直接修复，保留 Issue 并升级为 Spec（门槛原文见 [AGENTS.md](../../AGENTS.md) 改动流程第 5 条），Spec 确认后按需创建 Plan：

- 修复需要跨模块协调、多阶段实施且步骤之间存在明显依赖；
- 需要改变公共契约、公共接口、持久化格式或安全边界；
- 根因涉及架构设计，局部修补会掩盖系统性问题；
- 需要重新确定目标、范围、兼容策略或回滚方案，或范围风险已超出原 Issue。

升级后的目标、范围、设计、验收和实施以 Spec 及其可选 Plan 为准，不在 Issue 内复制设计、验收证据或实施步骤。Issue 原 AC 停止演进，实施期间保持“进行中”，只有 Spec 已完成且原问题路径已验证后才能改为“已完成”。

## 命名与关联

- 文件名为 `YYYYMMDDHH-issue-<topic>.md`，例如 `2026110707-issue-cli-empty-input.md`。
- 时间前缀使用 Issue 首次创建时的本地时间，格式为四位年份、两位月份、日期和 24 小时制小时；`<topic>` 使用小写 kebab-case，简要描述问题而非修复动作。
- 一份 Issue 只记录一个问题；不同根因或独立验收的问题分别创建。
- 升级为 Spec 后，在 Issue 中添加 `../specs/YYYYMMDDHH-design-<topic>.md` 相对链接；通过 Spec 查找可选 Plan，不另设“关联计划”字段。
- 状态只使用“待处理／进行中／已完成／已关闭”，不增加“已升级”。未完成或不修复的 Issue 不得标记为“已完成”。

## 编写与修复流程

1. 记录实际现象、预期行为、复现条件和证据；无法稳定复现时明确说明限制和不确定性，不虚构复现。
2. 写清影响范围和初步边界，区分已确认事实与根因推测。
3. 开始修改修复对象前完成就绪检查；信息不足时可以先登记和调查，不直接修改实现。
4. 自动化回归适用时，先增加能复现问题的测试并确认其因原问题失败，再实施最小修复并确认测试转绿；无法自动化时记录人工操作、预期结果和不能自动化的原因，不虚构测试或修复前失败结果。
5. 修复开始后保持 AC 编号稳定；需要改变目标、范围或公共行为时按升级条件处理。
6. 收尾按相同 AC 编号记录真实结果、证据和未执行项：未升级的 Issue 满足完成门禁后改为“已完成”；升级后只引用 Spec 验收结论。
7. 不修复、重复或无法成立的问题标记为“已关闭”，说明关闭原因、实际改动和未验证项，不要求 AC 通过。
8. 长期架构、决策或排障知识按需回写对应权威文档，不复制到 Issue 长期维护。

## 修复前就绪检查

就绪检查约束实施，不妨碍先登记信息不完整的问题。开始修改修复对象前必须满足：

- 实际行为、预期行为和现有证据明确，复现稳定性与不确定性已说明；
- bug 根因已定位并有依据，或属于已说明理由的非缺陷型局部修正；
- 要改与不碰的路径具体，修复约束和明确不做的事项清楚；
- 未触发 Spec 升级条件；
- 每条 AC 都有场景与操作、可观察预期和可执行验证方式，原问题与回归路径已覆盖。

全部满足后才能修改修复对象。调查、证据收集和用于定位根因的回归测试可以先进行；未定位根因时不得借测试先行直接修改生产实现。

## 验收与追溯

- 验收编号、门禁与收尾规则与 [Spec 规范](../specs/README.md) 的“验收与追溯”一致：每条 AC 在 Issue 内唯一，包含类型、场景与操作、预期结果和验证方式；未升级的 Issue 收尾按相同编号记录“通过／失败／未执行／不适用”。
- 自动化回归适用时，保留修复前失败与修复后通过的结果或证据位置；失败必须符合原问题，不能把环境或测试自身错误当作复现成功。
- 修复开始后不得静默改写或复用 AC 编号；新增验收使用新编号并记录原因，触及升级条件时暂停直接修复。
- 升级后保留原验收表作为历史记录，将收尾的逐项结果表替换为 Spec 最终验收结论及原问题路径结论的引用，不维护第二份 AC 证据表。

## 内容约束

- 现象、根因和修复范围分开描述。
- 复现步骤使用最小、可操作的输入和环境，不包含密钥或真实用户数据。
- 预期和实际行为必须可观察、可核对；验证方式写测试名、命令或可复现人工操作，写到足以判定结果即可。
- 范围使用具体文件或模块路径，不使用“等相关文件”代替边界。
- 核心章节必填。以下条件内容在触发时必须写清：

| 触发条件 | 必须说明的内容 |
|---|---|
| bug 根因尚未定位 | 已确认事实、待验证假设和“待定位”；修改实现前补齐根因依据 |
| 非缺陷型局部修正 | 根因“不适用”的理由，以及当前行为到目标行为的变化 |
| 间歇、尚未复现或无法稳定复现 | 复现稳定性、现有证据、限制和不确定性，不虚构复现步骤 |
| 无法自动化验证 | 人工操作、预期结果和不能自动化的原因 |
| 升级为 Spec | Spec 链接、原 AC 停止演进，以及收尾对 Spec 最终结论的引用 |
| 纯文档修复 | 按 AGENTS.md 执行文档检查，并明确未运行的代码测试 |

- 不增加固定严重级别、负责人、标签、风险矩阵或回滚章节；触及高风险或公共契约时升级 Spec，不用额外字段绕过边界。
- 不复制其他工作文档正文，需要引用时使用相对链接；日志只保留安全摘要或证据位置。
- 复制模板后替换全部尖括号占位，按实际增删验收行并删除无关条件提示，不留空白示例、未决占位或无关章节。
- 文档使用一个 H1，标题逐级递进，代码围栏标注语言，链接路径大小写与磁盘一致。

## 内联模板

```markdown
# <问题标题>

> 状态：待处理 / 进行中 / 已完成 / 已关闭。
> 关联规格：<升级后的 Spec 相对链接；未升级时写“无”。>
> 完成后作为历史记录，不作为现行架构或行为的权威来源。

## 问题摘要

<一个可定位的问题及其影响。>

## 环境与复现

- 环境与前置条件：<相关版本、平台、配置或输入及复现所需状态；不适用则说明。>
- 复现步骤：
  1. <具体操作或命令。>
  2. <具体操作或命令。>
- 实际行为：<可观察结果或错误。>
- 预期行为：<可核对结果。>
- 复现稳定性与限制：<稳定 / 间歇 / 尚未复现；间歇或尚未复现时记录证据限制与不确定性，稳定时写“无”。>

## 证据与根因

- 证据：<日志摘要、测试失败、代码路径或最小样例，区分事实与推测。>
- 根因：<已确认根因及依据；尚未定位时写“待定位”，非缺陷型局部修正写“不适用”及理由。>

## 修复范围

- 要改：<具体文件或模块。>
- 不碰：<具体文件或模块。>
- 修复约束：<最小修复、兼容性和禁止扩大的边界。>

## 验收标准

| 编号 | 类型 | 场景与操作 | 预期结果 | 验证方式 |
|---|---|---|---|---|
| AC-01 | 原问题 | <复现条件及修复后的核对操作。> | <原问题消失的可观察结果。> | <测试名、命令或人工核对方法。> |
| AC-02 | 回归 | <新增或更新的回归检查；自动化时先确认修复前失败。> | <修复前因原问题失败、修复后通过，或人工检查符合预期。> | <具体验证方法及证据位置。> |
| AC-03 | 边界 / 异常 | <按适用性填写边界或异常输入；不适用时删除本行。> | <可观察结果及必要的异常回填。> | <具体验证方法。> |
| AC-04 | 契约 | <适用于本次修复的完整测试、lint、格式或文档检查。> | <适用检查通过，未执行项不隐瞒。> | <具体命令或文档检查方法。> |

## 明确不做

- <不属于本次局部修复的行为或目标；无则说明，不重复文件清单。>

## 收尾记录

<未升级时保留下表并复制覆盖全部 AC；升级时删除下表，只填写“升级验收”对 Spec 最终结论的引用。>

| 编号 | 结果 | 实际结果与证据 |
|---|---|---|
| AC-01 | 通过 / 失败 / 未执行 / 不适用 | <逐项填写真实结果、关键输出或证据位置。> |

- 升级验收：<未升级写“无”；升级时填写 Spec 收尾记录链接及原问题路径结论，不复制 Spec 验收表。>
- 实际修改：<最终修改内容；未修复则说明。>
- 根因结论：<最终确认根因；仍未知或非缺陷修正时明确说明。>
- 偏差与范围变化：<实际偏差、AC 变化原因或 Spec 升级情况；无则说明。>
- 补充检查与未执行说明：<非门禁检查结果和其他未执行项；无则说明。>
- 关闭原因：<仅已关闭 Issue 填写；否则写“无”。>
- 文档回写：<实际更新的权威文档；无则说明。>
```
